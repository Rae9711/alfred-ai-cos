# Design: Avatar interaction space (center tab button)

Generated by /office-hours on 2026-07-02
Status: APPROVED
Supersedes: none — this is a feature-level addition, not a replacement, to the
main Alfred product design doc from the same session.

## Problem Statement

The center tab button is the most prominent element in the app — a 54px avatar icon,
lifted above the tab bar, currently routing to `/capture` (Speak/Type/Snap/Forward
task capture). `COMPANION_AVATAR.md` states the original design intent was
"avatar-as-home in the center tab button," but Capture shipped there first as the MVP
wedge. The founder wants this slot to feel like interacting with Alfred directly, not
just filing a form.

## What This Actually Is

Working through what the founder described (tap-to-interact, telling the avatar about
upcoming events, asking it to note down what's on your mind, asking it to help with
things) revealed this is **not a new capability** — it's the existing Capture flow and
the existing task-grounded action interpreter (`interpret_and_act`), presented through
the avatar's voice instead of a form. The design problem is presentation, not new
backend capability.

## Constraints

- **Must not become open-ended companionship chat.** Earlier session premise: no
  unstructured chat with the avatar, interactions stay anchored to a real capture or
  a real request. Everything in this feature stays inside that boundary.
- **Proactive "butler remembers" behavior is explicitly out of scope for v1.** Alfred
  resurfacing something the user mentioned earlier, unprompted, is a real and good
  idea but requires new backend logic (deciding when/what to resurface) beyond
  re-presenting Capture. Deferred, not rejected.
- **Timing risk:** the founder's concierge test (3-5 friends, 2 weeks) is imminent and
  needs a *stable* core loop to produce a clean signal. This shaped the approach
  recommendation below.

## Premises

1. This space exists to make Capture + task-grounded help feel like talking to your
   butler — a presentation layer, not new capability.
2. The tap-to-interact avatar animation is cheap and worth building now — it uses the
   existing `AvatarState` mood system (idle/thinking/focused/success/error/sleep),
   already built, currently underused.
3. "Butler remembers" (proactive resurfacing) is a later phase.
4. The existing Capture screen's 4-tab mode structure (Speak/Type/Snap/Forward) may
   need to change shape to feel conversational — this is what Approach B (chosen
   below) actually redesigns.
5. Nothing here conflicts with the no-open-ended-chat guardrail.

## Approaches Considered

### Approach A: Reskin (Minimal Viable)
Keep the existing 4-tab Capture screen structure. Add the avatar tap-animation,
replace generic confirmation copy with warm butler-voiced language, reframe screen
copy to feel spoken-to rather than form-filled. Effort: S (human ~2-3 days). Risk:
Low. Reuses: entire existing CaptureScreen and extraction pipeline as-is.

### Approach B: Unified Conversational Intake (Ideal Architecture) — SELECTED
Replace the 4 separate mode tabs with one unified input the avatar "listens" to —
voice, typed text, and forwarded content all funnel into one intake. Alfred responds
with a brief acknowledgment naming what it understood, then hands back a card showing
what got created (task, reminder, event). Effort: M (human ~1-2wk). Risk: Medium —
real information-architecture redesign of a shipped, working feature, timed right
before the concierge test needs stability. Reuses: same `ParsedTask`/`CaptureResult`
extraction pipeline; new UI shell.

### Approach C: Avatar as Persistent Composer (Creative/Lateral)
A possible successor phase to B, not a mutually exclusive alternative: once the
unified conversational intake (B) exists and is proven, C makes that same intake
reachable as a floating, always-tappable affordance from anywhere in the app, not
just this one destination screen — closer to the original "avatar-as-home" intent.
Full Capture screen reserved for Snap/Forward only. Effort: L (human ~2-3wk). Risk:
High — app-wide navigation change. Not recommended now given imminent test timing;
revisit after B ships and stabilizes.

## Recommended Approach

The founder selected **Approach B**, consciously taking on more redesign risk than
the minimal reskin in exchange for a more complete experience. Sequencing decision
below exists specifically to manage that risk.

## Open Questions

- **Unified intake's exact interaction model:** voice/type/forward funnel into "one
  input" — the precise UI mechanics (single text field with a mic button? A
  chat-like transcript view? Something else?) need a design pass before
  implementation.
- **Tap-animation specifics:** which existing `AvatarState` mood plays on tap, and
  for how long — a concrete decision for whoever implements T-AV1.

## Success Criteria

- A user can tell Alfred something (event, note, request) through this space and get
  a warm, specific acknowledgment — not a generic "Task created" confirmation.
- The interaction never requires or invites unstructured back-and-forth chat.
- This ships and stabilizes **before** concierge-test friends are recruited, so the
  test's core daily loop (Gmail+Calendar triage, one-tap approve) is unaffected by it.

## Dependencies

- Depends on the near-term build order from the main design doc (chat grounding +
  SMS-in-context, and the Gmail/Calendar retry utility, both done as of this
  session).
- A design pass on the unified-intake interaction model before implementation
  starts, given Approach B genuinely redesigns a shipped screen.
